


# Ensure Privileged Accounts Are Not Delegated

## Microsoft Security Recommendation

Microsoft Defender recommends ensuring that **privileged accounts are not delegated** to prevent credential reuse, lateral movement, and full domain compromise through Kerberos abuse.

This control is a **Tier‑0 identity security requirement** in Active Directory environments.

---

## 1. Simple Explanation (High‑Level)

**Delegation** allows a service or computer to **reuse a user’s credentials** to access another service on the user’s behalf.

This is required for some applications, but **it must never apply to privileged accounts**.

> If a privileged account is delegable and logs onto a compromised system, its credentials can be reused without knowing the password.

---

## 2. Why Delegation Exists (Legitimate Use Case)

Example: multi‑tier application

```

User → Web Server → Database Server

```

- User authenticates to the Web Server
- Web Server needs to access the database **as the user**
- Delegation avoids repeated logins

✅ Legitimate for **normal users**  
❌ Dangerous for **privileged accounts**

---

## 3. Types of Delegation (Important)

### 3.1 Unconstrained Delegation (Most Dangerous)

- Service can impersonate the user to **any service**
- Kerberos Ticket Granting Ticket (TGT) may be cached
- If compromised, attacker gets reusable tickets

🚨 **Never allowed for privileged accounts**

---

### 3.2 Constrained Delegation

- Delegation allowed only to specific services
- Limits blast radius
- Still unsafe for privileged identities

---

### 3.3 Resource‑Based Constrained Delegation (RBCD)

- Target resource controls delegation
- More modern and secure
- Still **must exclude privileged accounts**

---

## 4. How Delegation Works at Kerberos Ticket Level

### Normal Kerberos (No Delegation)

```

Client → KDC → Service

```

- Client gets a **non‑forwardable TGT**
- Service cannot reuse it elsewhere

---

### Kerberos With Delegation Enabled

```

+------------------+        Kerberos Tickets        +------------------+
\| Client (User)    | ----------------------------> | Front‑end Server |
+------------------+                               +------------------+
|
\| Delegated ticket
v
+------------------+
\| Back‑end Service |
+------------------+

```

Key difference:
- The client’s **forwardable TGT** is stored or reused
- Service can request tickets **as the user**

---

### Why This Breaks Security for Privileged Accounts

If a **privileged user** logs on to a delegated server:
- Their Kerberos tickets become reusable
- A compromised server can impersonate the admin
- No password theft required
- No MFA prompt required

> Delegation turns “logon once” into **“permanent reuse”**

---

## 5. Real‑World Attack Scenario

1. Domain Admin logs into an application server
2. Server is configured for delegation
3. Attacker compromises the server
4. Attacker extracts delegated Kerberos tickets
5. Attacker accesses Domain Controllers

```

Delegated Server (Compromised)
|
\| Uses admin ticket
v
Domain Controller

```

✅ Silent  
✅ Credential‑less  
✅ Catastrophic  

---

## 6. What Accounts Are Considered Privileged

Examples include:
- Domain Admins
- Enterprise Admins
- Schema Admins
- Built‑in Administrator
- Tier‑0 service accounts
- Any custom high‑privilege roles

> **None of these accounts should ever be delegable**

---

## 7. How to Find Delegated Privileged Accounts

### 7.1 What to Look For

You are looking for privileged accounts that:
- Are **not protected**
- Can have their credentials delegated

Specifically:
- Accounts **not marked as sensitive**
- Accounts trusted for delegation
- Accounts able to generate forwardable Kerberos tickets

---

### 7.2 Key AD Attribute (Conceptual)

The critical protection bit is:

> **“Account is sensitive and cannot be delegated”**

If this is **not enabled** on a privileged account:
- The account **can be delegated**
- Even if delegation is not explicitly configured elsewhere

---

### 7.3 Common Findings in Real Environments

| Finding | Why It Happens |
|------|---------------|
| Domain Admin not marked sensitive | Legacy default |
| Service account in admin group | Convenience |
| Admin used for app testing | Bad practice |
| No tiered admin model | Design gap |

---

## 8. Safe Remediation (Do NOT Break Apps)

❗ You do NOT remove delegation from servers blindly  
❗ You protect **accounts**, not applications  

---

### ✅ Step 1 – Identify Privileged Accounts
- Domain Admins
- Enterprise Admins
- Custom Tier‑0 groups
- Sensitive service accounts

---

### ✅ Step 2 – Mark Privileged Accounts as Sensitive

Enable:

```

Account is sensitive and cannot be delegated

```

Effect:
- Kerberos will NOT issue forwardable tickets
- Even if service supports delegation
- Application delegation continues for non‑admin users

✅ Safe  
✅ No reboot  
✅ No service outage  

---

### ✅ Step 3 – Enforce Admin Usage Discipline

- Privileged accounts should log on only to:
  - Domain Controllers
  - Privileged Access Workstations (PAWs)
- Never to application or user servers

---

### ✅ Step 4 – Monitor After Change

After marking accounts sensitive:
- Watch for:
  - Application authentication failures
  - Kerberos errors
- Failures usually indicate:
  - Privileged account incorrectly used by an app
  - Design issue that must be corrected

---

## 9. What NOT to Do

❌ Do not remove delegation from all servers  
❌ Do not break valid application flows  
❌ Do not exempt privileged accounts “temporarily”  
❌ Do not allow admins to log into delegated machines  

---

## 10. How This Control Protects the Domain

This recommendation:
- Blocks Kerberos‑based lateral movement
- Prevents credential reuse
- Stops silent admin impersonation
- Completes Tier‑0 identity hardening

It complements:
- NTLM disablement
- LDAP signing and encryption
- DCSync restriction

---

## 11. One‑Sentence Executive Summary

> **Delegation allows credential reuse; ensuring privileged accounts are marked as non‑delegable prevents attackers from reusing high‑privilege Kerberos tickets obtained from compromised systems.**

---

## ✅ Final Takeaway

- ✅ Delegation is required for applications
- ❌ Privileged accounts must never be delegable
- ✅ This is a configuration‑based, proactive control
- ✅ Fixing this eliminates a major Kerberos abuse path
