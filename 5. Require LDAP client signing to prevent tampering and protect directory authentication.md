# Require LDAP Client Signing to Prevent Tampering and Protect Directory Authentication

## Microsoft Security Recommendation

Microsoft Defender recommends requiring LDAP client signing to protect LDAP communications from tampering and man‑in‑the‑middle attacks.

This control ensures the **integrity of LDAP traffic**, preventing attackers from modifying directory authentication requests and responses in transit.

---

## 1. What Is LDAP Client Signing?

**LDAP client signing** ensures that every LDAP request and response is:
- Digitally **signed**
- Verified for **integrity**
- Protected against modification in transit

LDAP signing **does not encrypt data** (that is LDAPS / LDAP sealing), but it **guarantees integrity and authenticity**.

> ✅ Signing makes sure data is not altered  
> ✅ Encryption makes sure data cannot be read  
> 🔐 Strong security uses **both**

---

## 2. Why LDAP Client Signing Is Important

Without LDAP signing:
- LDAP traffic can be intercepted and **modified**
- Attackers can inject or alter:
  - Authentication responses
  - Group membership queries
  - Authorization decisions

This enables:
- Privilege escalation
- Authentication bypass
- AD reconnaissance manipulation

---

## 3. Real‑World Attack Scenario (Unsigned LDAP)

### 🔴 LDAP Without Signing (Vulnerable)

```

+----------------+                +----------------------+
\| LDAP Client    |                | Domain Controller    |
\| (App / Device) |                |                      |
+----------------+                +----------------------+
\|                                      |
\| LDAP Bind / Query                    |
\|------------------------------------>|
\|   (Unauthenticated integrity)       |

```

❌ An attacker on the network can:
- Modify responses
- Inject fake group memberships
- Alter query results

---

## 4. Secure LDAP With Client Signing

### ✅ LDAP With Signing Enabled

```

+----------------+                +----------------------+
\| LDAP Client    |                | Domain Controller    |
\| (Signed LDAP)  |                |                      |
+----------------+                +----------------------+
\|                                      |
\| Signed LDAP Bind / Query             |
\|------------------------------------>|
\| Integrity Verified                  |

```

✅ DC verifies request integrity  
✅ Tampering is detected and rejected  

---

## 5. How LDAP Client Signing Works

LDAP client signing uses:
- **Kerberos authentication**
- Integrity checks (cryptographic signatures)
- Mutual trust between client and DC

Key points:
- Only **Kerberos‑authenticated clients** can sign LDAP
- NTLM‑based LDAP cannot sign
- Domain‑joined systems support this by default

---

## 6. Difference Between LDAP Signing and LDAP Encryption

| Feature | LDAP Signing | LDAP Encryption (LDAPS) |
|------|-------------|--------------------------|
| Protects integrity | ✅ Yes | ✅ Yes |
| Protects confidentiality | ❌ No | ✅ Yes |
| Prevents tampering | ✅ Yes | ✅ Yes |
| Prevents sniffing | ❌ No | ✅ Yes |

> ✅ Best practice: **Require signing + enforce encryption where possible**

---

## 7. Why Microsoft Defender Flags This Recommendation

This is a **configuration‑based exposure recommendation**, not an incident alert.

Defender detects:
- LDAP client signing not required
- DCs accepting unsigned LDAP binds
- Potential MITM and relay attack surface

Even if:
- No attacks observed
- LDAP encryption is enabled

Unsigned LDAP is still considered **high risk**.

---

## 8. Detecting Unsigned LDAP Clients

### 8.1 LDAP Signing Event IDs (Domain Controllers)

Logged in:

```

Applications and Services Logs →
Directory Service

```

| Event ID | Description |
|--------|-------------|
| 2886 | LDAP signing not required |
| 2887 | Count of unsigned or non‑signed binds |
| 2888 | Unsigned bind from specific client |
| 2889 | Detailed client and account info |

Event IDs **2888 / 2889** identify:
- Source IP
- Application
- Account used

---

## 9. Safe Phased Implementation Plan (CRITICAL)

❗ **Do NOT enforce client signing without auditing first**

---

### ✅ Phase 1 – Audit Mode (No Impact)

Verify unsigned LDAP activity via event logs.

```

Domain controller: LDAP server signing requirements
→ None

```

Monitor Event IDs **2888 / 2889**.

---

### ✅ Phase 2 – Remediate Non‑Compliant Clients

For each unsigned LDAP client:
- Upgrade application
- Configure Kerberos authentication
- Replace NTLM‑based LDAP usage
- Switch to LDAPS if signing unsupported

Common offenders:
- Legacy Java apps
- Network devices
- Old appliances

---

### ✅ Phase 3 – Enforce LDAP Client Signing

```

Domain controller: LDAP server signing requirements
→ Require signing

```

✅ Unsigned LDAP binds are rejected  
✅ NTLM‑based LDAP fails  
✅ Only secure clients succeed

## 11. Registry Equivalent (For Reference)

> ⚠️ Use GPO for enterprise environments

```reg
HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters
LDAPServerIntegrity = 2
````

Value meanings:

*   `0` = None
*   `1` = Sign if negotiated
*   `2` = Require signing

🔁 Domain Controller restart required.
