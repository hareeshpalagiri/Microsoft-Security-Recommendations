
***

## What is this recommendation actually talking about?

**“Remove unnecessary replication permissions for Entra Connect AD DS Connector Account”**

In simple terms, Microsoft is saying:

> 👉 *Your Entra Connect service account might have **Domain‑Controller‑like replication powers** that it doesn’t always need.  
> If you’re not using a specific feature (Password Hash Sync), remove those powers to reduce risk.*

***

## Step 1: What is the Entra Connect AD DS Connector Account?

When you install **Microsoft Entra Connect** (formerly Azure AD Connect):

*   It syncs identities from **on‑prem Active Directory → Entra ID**
*   To do this, it uses a **service account in AD**

That account is usually:

*   Named something like `MSOL_6f3c2a9e7`
*   Called the **AD DS Connector Account**

### What this account does normally

*   Reads users, groups, computers
*   Reads attributes
*   Writes limited attributes (based on features you enabled)

✅ It is **not** a Domain Admin  
✅ It is **not** an Enterprise Admin  
✅ But it still needs **special permissions**

***

## Step 2: What are “Replication Permissions” in AD?

This is the **key part**.

In Active Directory, there are **very powerful permissions** called:

*   **Replicating Directory Changes**
*   **Replicating Directory Changes All**

Normally, **only Domain Controllers** have these.

### What do these permissions allow?

They allow an account to:

*   Perform **DCSync**
*   Act *like a Domain Controller*
*   Replicate sensitive data from AD, including:
    *   Password hashes
    *   Kerberos secrets
    *   Account credentials

⚠️ These permissions are **extremely sensitive**.

***

## Step 3: Why does Entra Connect ever need replication permissions?

Because of **Password Hash Synchronization (PHS)**.

### Password Hash Sync explained simply

*   AD stores **password hashes**
*   Entra ID needs a copy (hashed again) for cloud authentication
*   To read password hashes securely, Entra Connect must:
    *   Replicate them from AD
    *   Which requires **replication permissions**

✅ If **PHS is enabled**, replication permissions are REQUIRED  
❌ If **PHS is NOT enabled**, replication permissions are NOT required

***

## Step 4: The 3 common Entra Connect authentication modes

This is where people get confused.

| Method                                | Needs replication permissions? | Why                     |
| ------------------------------------- | ------------------------------ | ----------------------- |
| **Password Hash Sync (PHS)**          | ✅ Yes                          | Needs password hashes   |
| **Pass‑Through Authentication (PTA)** | ❌ No                           | Password validated live |
| **AD FS / Federation**                | ❌ No                           | Auth handled by ADFS    |

👉 **Only PHS requires these permissions**

***

## Step 5: So what is the security issue?

In many environments:

*   Entra Connect was installed with **default settings**
*   PHS was enabled *temporarily* or by accident
*   Later the org moved to **PTA or ADFS**
*   But the **replication permissions were never removed**

Result:

*   The `MSOL_*` account still has **DCSync‑level permissions**
*   Even though it doesn’t need them anymore

***

## Step 6: Why Microsoft considers this dangerous

Let’s think like an attacker.

### If an attacker compromises the MSOL account:

If it **has replication permissions**:

*   They can dump:
    *   All user password hashes
    *   Domain Admin hashes
*   They can fully compromise AD
*   This often goes **undetected** because it’s a *service account*

If it **does NOT have replication permissions**:

*   Attack impact is limited
*   No DCSync
*   No full domain takeover

✅ This is a **blast‑radius reduction control**

***

## Step 7: What Defender / Secure Score is checking

Microsoft Defender for Identity looks at:

*   Does the Entra Connect AD DS Connector account have:
    *   Replicating Directory Changes?
    *   Replicating Directory Changes All?
*   Is Password Hash Sync actually needed?

If Defender **sees replication perms**, it raises:

> **“Remove unnecessary replication permissions…”**

⚠️ Defender does **not always perfectly detect** if PHS is used *as a fallback*  
That’s why Microsoft expects **you to verify manually**

***

## Step 8: Very important nuance (this causes many incidents)

### ⚠️ PTA with PHS fallback

Some environments use:

*   **PTA as primary**
*   **PHS as backup**

In this case:

*   Password Hash Sync is technically **enabled**
*   Replication permissions **must stay**
*   Removing them will break password sync

👉 This is why you **must never remove blindly**

***

## Step 9: Mental model to remember (easy)

Think of replication permissions like this:

> **“Domain Controller powers”**

Ask yourself:

*   Does Entra Connect *need DC powers* in my design?

If:

*   ✅ Using PHS → **Yes**
*   ❌ Not using PHS → **Absolutely not**

***

## Step 10: Summary (concept only)

✅ The MSOL / AD DS Connector account sometimes has **replication (DCSync) rights**  
✅ These rights are **only required** for Password Hash Sync  
✅ If PHS is not used, these permissions are **dangerous and unnecessary**  
✅ Removing them:

*   Reduces attack surface
*   Prevents silent domain compromise paths
*   Aligns with Zero Trust & least privilege

***

> ⚠️ **Golden rule:**  
> **Never remove replication permissions until ALL checks below are completed and understood.**

# Step‑by‑Step: How to CHECK before removing replication permissions

(Entra Connect AD DS Connector Account)

***

## STEP 1: Identify the Entra Connect AD DS Connector Account

First, you must be **100% sure** which account we’re talking about.

### Why this matters

Many orgs have:

*   Multiple MSOL accounts
*   Old/stale Entra Connect servers
*   Staging mode servers

Removing permissions from the **wrong account** = sync failure.

***

### ✅ How to identify it

Run on a DC or management server:

```powershell
Get-ADUser -Filter {Name -like "MSOL_*"} |
Select Name, DistinguishedName
```

Typical output:

    Name            : MSOL_6f3c2a9e7
    DistinguishedName : CN=MSOL_6f3c2a9e7,CN=Users,DC=corp,DC=com

✅ Note down:

*   Account name
*   Distinguished Name (DN)
*   Domain/forest

***

## STEP 2: Confirm which Entra Connect server is ACTIVE

### Why this matters

*   Some orgs have **staging mode** Entra Connect servers
*   Replication permissions may be required on **only one active server**
*   Removing prematurely can break auth

***

### ✅ Check on Entra Connect server

Open **Synchronization Service Manager**  
or run:

```powershell
Get-ADSyncScheduler
```

Key values:

*   `SyncCycleEnabled = True`
*   `StagingMode = False`

✅ This confirms:

*   This server is actively syncing
*   This MSOL account is currently used

***

## STEP 3: Check which sign‑in method is actually in use

(**THIS IS THE MOST IMPORTANT STEP**)

### You are checking:

> **Does my environment use Password Hash Synchronization (PHS)?**

Because:

*   ✅ If **YES** → Stop here ❌ **DO NOT REMOVE**
*   ✅ If **NO** → Continue safely

***

### ✅ Run the official Microsoft diagnostic

On the Entra Connect server:

```powershell
Import-Module ADSyncDiagnostics
Invoke-ADSyncDiagnostics -PasswordSync
```

***

### ✅ Interpret the output

#### ✅ Case 1: SAFE to continue

    Password Hash Synchronization is disabled

➡️ Replication permissions **not required**

***

#### ❌ Case 2: DO NOT REMOVE

    Password Hash Synchronization is enabled

➡️ Replication permissions **mandatory**

***

#### ⚠️ Case 3: VERY COMMON TRAP

    Password Hash Synchronization cloud configuration is enabled

This usually means:

*   PTA is primary
*   **PHS is enabled as fallback**

➡️ ✅ Replication permissions **STILL REQUIRED**

***

## STEP 4: Confirm sign‑in method in Entra portal

### Why both checks?

Because Defender & Secure Score sometimes miss fallback configurations.

***

### ✅ In Entra Admin Center

Path:

    Entra ID
    → Hybrid management
    → Microsoft Entra Connect
    → Sign‑in method

Check which is **enabled**:

*   Password Hash Sync
*   Pass‑through Authentication
*   Federation

***

### ✅ Decision matrix

| What you see       | Safe to remove? |
| ------------------ | --------------- |
| PHS enabled        | ❌ NO            |
| PTA only, no PHS   | ✅ YES           |
| PTA + PHS fallback | ❌ NO            |
| Federation only    | ✅ YES           |

***

## STEP 5: Verify replication permissions are actually present

Before removal, confirm the problem exists.

***

### ✅ Check permissions using DSACLs

```powershell
$account = "DOMAIN\MSOL_6f3c2a9e7"
$domainNC = (Get-ADRootDSE).defaultNamingContext

dsacls $domainNC | findstr MSOL
```

Look for permissions like:

*   `Replicating Directory Changes`
*   `Replicating Directory Changes All`

✅ If present → Defender recommendation is valid  
✅ If not present → Recommendation might already be resolved

***

## STEP 6: Check if the account is over‑privileged elsewhere

### Why?

Some environments **manually over‑assign rights**.

Check:

*   Domain Admins ❌
*   Enterprise Admins ❌
*   Built‑in groups ❌

```powershell
Get-ADPrincipalGroupMembership MSOL_6f3c2a9e7
```

✅ Expected:

*   Only **Domain Users**
*   No privileged groups

***

## STEP 7: Check for recent password‑sync activity (sanity check)

Even if you *think* PHS is disabled, verify no activity depends on it.

***

### ✅ In Event Viewer (Entra Connect server)

Path:

    Applications and Services Logs
    → Directory Synchronization

Look for:

*   Password hash sync success/failure events

✅ No password sync events → safe signal  
❌ Active password sync events → STOP

***

## STEP 8: Understand Defender / Secure Score behavior (important context)

Microsoft Defender:

*   Detects **permissions**
*   Not always **feature dependency**

So sometimes:

*   Recommendation appears
*   But removal would break fallback auth

✅ That’s why **manual verification is mandatory**

***

## STEP 9: Final GO / NO‑GO checklist ✅

Before removal, **ALL must be true**:

✅ MSOL account identified and confirmed  
✅ Active Entra Connect server identified  
✅ `Invoke-ADSyncDiagnostics -PasswordSync` shows **disabled**  
✅ Entra Portal confirms **no PHS**  
✅ No password hash sync events  
✅ Replication permissions confirmed present  
✅ Change approved & documented

If **any one is false** → ❌ STOP

***

## Mental shortcut to remember

> **Replication permission = DCSync power**

Ask one question:

> “Does Entra Connect still need *password hashes*?”

If:

*   ✅ Yes → **Keep permissions**
*   ❌ No → **Remove permissions**

# How to Remove Replication Permissions **Safely**

## (Entra Connect AD DS Connector Account)

***

## High‑level safety principles (read first)

✅ Do **not** delete the account  
✅ Do **not** reset the password during this change  
✅ Do **not** remove permissions blindly  
✅ Always remove **only replication permissions**  
✅ Always validate after removal

***

## Step 1: Prepare (Change hygiene)

### ✅ What to note down

*   MSOL account name & DN
*   Entra Connect server name
*   Sync method (PTA / Federation)
*   Change window

Example:

```text
Account: MSOL_6f3c2a9e7
DN: CN=MSOL_6f3c2a9e7,CN=Users,DC=corp,DC=com
Server: AADCONNECT01
```

***

## Step 2: Log in with the RIGHT credentials

You must use an account with:

*   **Enterprise Admin** or
*   **Domain Admin** permissions

✅ Use a **Jump Box / privileged workstation** if possible  
❌ Do not do this from random admin desktops

***

## Step 3: Confirm replication permissions again (last chance)

Run on a DC or RSAT machine:

```powershell
$account = "DOMAIN\MSOL_6f3c2a9e7"
$domainNC = (Get-ADRootDSE).defaultNamingContext

dsacls $domainNC | findstr MSOL
```

You should see lines like:

*   Replicating Directory Changes
*   Replicating Directory Changes All

✅ This confirms what will be removed  
❌ If nothing shows, stop — nothing to remove

***

## Step 4: SAFEST removal method (Microsoft‑supported)

### ✅ Preferred method: Use Entra Connect permission tooling

This **re-applies least‑privilege permissions** instead of bluntly stripping ACLs.

Run **on the Entra Connect server**:

```powershell
Import-Module "C:\Program Files\Microsoft Azure Active Directory Connect\AdSyncConfig\AdSyncConfig.psm1"
```

Then apply **basic read permissions only**:

```powershell
Set-ADSyncBasicReadPermissions `
 -ADConnectorAccountDN "CN=MSOL_6f3c2a9e7,CN=Users,DC=corp,DC=com"
```

✅ This:

*   Removes replication permissions
*   Keeps required read permissions intact
*   Is **Microsoft‑supported**

***

## Step 5: Alternative (manual) method – use ONLY if needed

⚠️ Use this **only** if the ADSync module is unavailable.

```powershell
$accountDN = "CN=MSOL_6f3c2a9e7,CN=Users,DC=corp,DC=com"
$domainNC = (Get-ADRootDSE).defaultNamingContext

dsacls $domainNC /R $accountDN
```

⚠️ This removes **explicit permissions only**  
⚠️ Do NOT remove inheritance unless you fully understand the ACL model

***

## Step 6: Force delta sync immediately

On Entra Connect server:

```powershell
Start-ADSyncSyncCycle -PolicyType Delta
```

✅ Sync should complete without errors  
❌ If sync fails → stop and investigate

***

## Step 7: Validate functionality (MANDATORY)

### ✅ Check sync status

```powershell
Get-ADSyncScheduler
```

Expected:

*   `SyncCycleEnabled = True`
*   No errors

***

### ✅ Check Event Viewer (Entra Connect server)

Path:

    Applications and Services Logs
    → Directory Synchronization

✅ No new errors  
✅ No password hash sync errors (expected)

***

### ✅ Sanity test authentication

*   Test login to Microsoft 365 / Entra ID
*   PTA or Federation sign‑in should work normally

***

## Step 8: Validate permissions are gone

Run again:

```powershell
dsacls $domainNC | findstr MSOL
```

✅ Replication permissions should **not appear**  
✅ Basic read permissions remain

***

## Step 9: Defender & Secure Score confirmation

*   Microsoft Defender for Identity:
    *   Recommendation → **Resolved**
*   Secure Score:
    *   Updated within \~24 hours

✅ No further action required

***

## Step 10: Rollback (if something goes wrong)

### ⚠️ ONLY re‑grant permissions if PHS is required

```powershell
Set-ADSyncPasswordHashSyncPermissions `
 -ADConnectorAccountDN "CN=MSOL_6f3c2a9e7,CN=Users,DC=corp,DC=com"
```

Then:

```powershell
Start-ADSyncSyncCycle -PolicyType Delta
```

✅ Restores replication permissions safely

***

## Common mistakes to avoid (very important)

❌ Removing permissions while PHS fallback exists  
❌ Removing permissions from the wrong MSOL account  
❌ Doing this on staging servers only  
❌ Removing “Log on as a service” rights  
❌ Deleting or recreating MSOL account

***

## Mental safety checklist (remember this)

✅ No Password Hash Sync  
✅ Least privilege only  
✅ Re‑apply permissions, don’t “rip ACLs”  
✅ Validate immediately  
✅ Defender must turn green

***

## What this achieves (why it’s worth doing)

✅ Removes **DCSync‑level power** from MSOL account  
✅ Prevents stealth domain compromise path  
✅ Aligns with Zero Trust & Tier‑0 model  
✅ Zero user impact when done correctly
