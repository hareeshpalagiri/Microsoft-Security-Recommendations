

# ✅ Microsoft Security Recommendation

## Remove non‑admin accounts with DCSync permissions

***

## 1. What is DCSync? (Plain English First)

**DCSync** is a legitimate **Active Directory replication function**.

Domain Controllers regularly **synchronize directory data** with each other.  
To do this, a DC is allowed to:

*   Request **password hashes**
*   Request **Kerberos keys**
*   Request **sensitive account secrets**

from another Domain Controller.

This process is called **Directory Replication**.

👉 **DCSync = “Act like a Domain Controller and ask AD for secrets”**

***

## 2. How DCSync Normally Works (Legitimate Scenario)

### Normal AD behavior:

    +-------------------+        Replication        +-------------------+
    | Domain Controller | <----------------------> | Domain Controller |
    |       DC1         |                          |        DC2        |
    +-------------------+                          +-------------------+

*   Only **Domain Controllers**
*   Or **highly trusted admin accounts**
*   Can perform directory replication

This is **expected and required** for Active Directory to function.

***

## 3. What Permissions Allow DCSync?

DCSync is not a single checkbox.

It is controlled by **three Active Directory permissions** on the **domain object**:

1.  **Replicating Directory Changes**
2.  **Replicating Directory Changes All**
3.  **Replicating Directory Changes in Filtered Set**

If an account has these permissions:

> It can request **password hashes for any account in the domain**

✅ Including:

*   Domain Admins
*   Enterprise Admins
*   krbtgt account

***

## 4. Why This Is Extremely Dangerous

### 🔥 The core risk

A user with DCSync permissions can:

*   Dump **all password hashes**
*   Dump **Kerberos ticket‑granting keys**
*   Do this **remotely**
*   Without malware
*   Without touching LSASS
*   Without even logging on to a DC

This means:

> **One compromised user account = full domain compromise**

***

## 5. Real‑World Attack Scenario (Very Important)

### Scenario: Attacker Gets DCSync Rights

1.  Attacker compromises a **low‑privileged service account**
2.  That account has **DCSync permissions**
3.  Attacker runs tools like:
    *   `mimikatz`
    *   `secretsdump.py`
4.  AD happily responds:
    *   “Here are all your domain secrets”

<!---->

    +---------------------+        DCSync Request        +-------------------+
    | Compromised Account | --------------------------> | Domain Controller |
    |   (Not an Admin!)   |                             |                   |
    +---------------------+                             +-------------------+
                 |
                 | Receives:
                 | - NTLM hashes
                 | - Kerberos keys
                 | - krbtgt secret

✅ Game over. Domain is owned.

***

## 6. Why Microsoft Specifically Says “Non‑Admin Accounts”

Some accounts **must** have DCSync permissions:

*   Domain Controllers
*   Domain Admins
*   Enterprise Admins (rare cases)

But **many environments accidentally give these rights to**:

*   Legacy service accounts
*   Backup accounts
*   Monitoring tools
*   Automation users
*   Migration leftovers
*   Human accounts (very bad)

Microsoft Defender flags:

> **Any account that is NOT a built‑in administrative principal but still has DCSync rights**

Because these accounts are:

*   Less protected
*   More likely targeted
*   Often forgotten

***

## 7. Why You Might Not See an Alert but Still Be at Risk

This recommendation is **configuration‑based**, not detection‑based.

Defender does NOT require:

*   A DCSync attack
*   A suspicious event
*   Malware activity

It simply checks:

*   *“Who currently has replication permissions?”*

If non‑admin accounts appear → recommendation is triggered.

This means:

> **You may be perfectly “quiet” but still dangerously exposed.**

***

## 8. Accounting for Real‑World Environments

### Common legitimate‑looking but risky cases:

| Account Type           | Why It Happens        | Risk      |
| ---------------------- | --------------------- | --------- |
| Backup service account | Old AD backup tools   | Very High |
| Migration account      | AD migration projects | High      |
| Monitoring account     | Over‑permissioned     | High      |
| App service account    | Copied permissions    | Critical  |
| Human user             | Misconfiguration      | Severe    |

Many of these accounts:

*   Do not use MFA
*   Have passwords that don’t rotate
*   Are synced to scripts or apps

***

## 9. What Microsoft Actually Wants You to Achieve

The goal is **not**:

> “Remove all DCSync permissions”

The goal **is**:

> **Ensure only Domain Controllers and explicitly approved admin accounts can replicate AD data**

In modern best practice:

*   ✅ Only DC computer accounts
*   ✅ Maybe a very small number of Tier‑0 admin accounts
*   ❌ No service accounts
*   ❌ No user accounts
*   ❌ No app identities

***

## 10. How This Fits into the Bigger Identity Hardening Story

This recommendation directly complements:

*   ✅ Disable NTLM (prevents credential abuse)
*   ✅ Encrypt LDAP (protects credentials in transit)
*   ✅ Require LDAP signing (prevents tampering)
*   ✅ **Restrict DCSync (protects directory secrets at rest)**

Think of it as:

> **NTLM / LDAP protect how credentials travel  
> DCSync protects who can extract *all* credentials**

***

## 11. Clear One‑Sentence Explanation (Reusable)

You can confidently say:

> **DCSync permissions allow an account to impersonate a Domain Controller and replicate Active Directory secrets such as password hashes; removing these permissions from non‑admin accounts prevents full domain compromise if such accounts are breached.**

***

## ✅ Summary

*   ✅ DCSync is a powerful, legitimate AD feature
*   ❌ In the wrong hands, it breaks the entire domain
*   ✅ Defender flags **non‑admin DCSync permissions** as critical
*   ✅ Fixing this greatly improves identity security
*   ✅ This recommendation is **high severity, high value**
